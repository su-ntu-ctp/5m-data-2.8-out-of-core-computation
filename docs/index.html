Out-of-Core Computation

What happens when your dataset is bigger than your computer's memory — and how Polars lets you process it anyway, without upgrading your RAM.

01 · The Problem

When data outgrows memory

Tools like pandas load an entire file into RAM before you can touch it. That works fine for a 5 MB spreadsheet. It breaks down fast once files get into the hundreds of megabytes or gigabytes — exactly the size of real datasets like ratings.csv (26 million rows) or taxi_trip_data.csv (~1.5 GB).

Analogy

RAM is your desk — small, fast, but limited space to work on. Disk is your filing cabinet — huge, but slow to dig through. Loading a whole file into RAM is like dumping every filing cabinet drawer onto your desk at once. Eventually there's nowhere left to put anything, and the process crashes with a MemoryError.

02 · The Concept

What is out-of-core computation?

Out-of-core computation means processing data that does not fit entirely in memory (RAM) by working on it in smaller pieces, reading and discarding chunks from disk as needed — instead of requiring the whole dataset to be resident in memory at once. ("Core" is an old term for memory.)

In-core

The whole dataset is read into RAM first. Fast to query afterwards, but the load step itself can exhaust memory on large files.

  • pd.read_csv(...)
  • pl.read_csv(...)

Out-of-core

Data is streamed through in chunks. Only a small window of rows sits in memory at any moment, no matter how large the file is.

  • pl.scan_csv(...)
  • .collect(streaming=True)

04 · Lazy Evaluation

Eager vs. lazy execution

Out-of-core processing in Polars is built on top of lazy evaluation. Instead of running each step immediately, Polars first builds a query plan, optimizes it, then runs the optimized version in one pass.

Every line executes immediately and materializes a full result before the next line runs.

group_by()
→
agg()

sort()
# each step runs the instant it is called
result = (
    metadata_pl
    .group_by("original_language")
    .agg(
        pl.mean("revenue").alias("avg_revenue"),
        pl.mean("runtime").alias("avg_runtime"),
    )
    .sort("avg_revenue", descending=True)
)

Calling .lazy() builds a query plan first. Nothing runs until .collect() — by then, Polars has optimized the whole plan into one efficient pass.

lazy()
→
group_by()
→
agg()
→
sort()
→
collect()
q = (
    metadata_pl.lazy()
    .group_by("original_language")
    .agg(
        pl.mean("revenue").alias("avg_revenue"),
        pl.mean("runtime").alias("avg_runtime"),
    )
    .sort("avg_revenue", descending=True)
)
result = q.collect()  # nothing ran until this line
Why it matters

Because Polars sees the whole plan before running anything, it can reorder, combine, or skip steps — e.g. pushing a filter down before a join so less data ever needs to be touched. That same query plan is also what makes streaming possible.

05 · Streaming

Processing data that doesn't fit in RAM

Swap read_csv for scan_csv and the file is no longer loaded — Polars just notes where it lives and what its schema is. Add streaming=True to .collect() and Polars pulls the file through the query plan in chunks, discarding each chunk once it's been processed.

q = (
    pl.scan_csv('data/taxi_trip_data.csv', try_parse_dates=True)
    .group_by("passenger_count")
    .agg(pl.mean("trip_distance").alias("avg_trip_distance"))
)
df_pl = q.collect(streaming=True)  # ~1.5 GB file, small constant RAM use

06 · Practical Workflow

How this looked in the lesson

Before running a full streaming query on the 1.5 GB taxi dataset, the notebook worked through the file in stages — never blindly loading the whole thing first.

Peek with a row limit

pl.read_csv('data/taxi_trip_data.csv', n_rows=100000) — read just 100k rows to inspect .schema and .head() cheaply.

Understand every column

Check the data dictionary before writing any query — knowing what passenger_count or trip_distance actually mean prevents wasted queries later.

Scan lazily, don't read eagerly

pl.scan_csv(..., try_parse_dates=True) builds a plan against the full file without loading it.

Collect with streaming on

.collect(streaming=True) runs the plan chunk by chunk, returning only the small aggregated result — e.g. min/max pickup times, or average trip distance per passenger count.

Key Takeaways

Remember this

  • "Out-of-core" means processing data larger than available RAM by streaming it in chunks from disk.
  • Polars is generally faster than pandas at reading and aggregating the same data, even before streaming is involved.
  • .lazy() + .collect() defers execution so Polars can optimize the whole query plan before running it.
  • scan_csv(...) + .collect(streaming=True) is the out-of-core pattern: scan lazily, then stream through in chunks.
  • Always peek at a large file first (n_rows=..., check the schema) before committing to a full scan.
